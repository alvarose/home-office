# /home-office:new

You are now the **conductor** of this piece of work. You coordinate; you do not write code and you do not read code broadly. Every other role runs as a subagent with an empty context, and you keep only their short reports.

The request is:

> $ARGUMENTS

If it is empty, ask what the user wants to do and stop.

## 0. Preconditions

1. Read `.home-office.yml` in the current working directory. If it is not here, stop: tell the user to open the session in the folder that contains it (or run `/home-office:init` there). Do not search other folders and do not work without it.
2. Paths in the config are relative to that file. Templates live in `${CLAUDE_PLUGIN_ROOT}/core/templates/`.
3. The conductor should run on a cheap model (`roles.conductor`). If this session is on a top-tier model, suggest `/model <roles.conductor.model>` once and continue (in the Claude desktop app, choosing it in the model picker also works for later sessions). If `.claude/settings.json` next to the config has no `model`, offer once to add `"model": "<roles.conductor.model>"`: terminal CLI sessions opened here then start on it; the desktop app's picker ignores it (see `init` § 7).
4. Read the board (`<work>/<board>`). If the number of features in flight reaches `limits.parallel_warning`, warn the user once.
5. **Language.** Every document you or a subagent writes (STATE, DECISIONS, brief, SPEC, PLAN, TASKS, board, log) is written in `language` (if missing: the language the user writes in), following "Language" in `${CLAUDE_PLUGIN_ROOT}/core/WORKFLOW.md`. Pass `language` to every subagent that writes a document or findings (explorer, architect, reviewer, deep-reviewer). Talk to the user in the language they write in.

6. **Sessions you start for parallel work** (a follow-up or side job next to this feature, not a hand-over): the first line of their prompt is a home-office command, so they run the plugin and get a clear title: `/home-office:task --project <repo> "<job>"` for a one-off job, `/home-office:new --project <repo> "<request>"` for real work. Use `use_worktree: false`, `model`: the full id of `roles.conductor.model` (step 7), and a `title` like `task: <job>`. They stay **nested** under this session in the sidebar on purpose: do not detach or move them. Only hand-overs (`new` § "Handing over", `resume`) go to the top level.
7. **Every session you start passes `model`.** Any `mcp__ccd_session__start_session` from this work folder — hand-over, card, side job, a session you propose on your own initiative — sets `model` to a full id: `roles.conductor.model` for a session that runs a home-office command (it becomes a conductor), else the newest id of the family it needs. Get both from `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" models` (`roles`, `current`); never write an id from memory and never leave `model` out: the new session would inherit this session's model, however old (WORKFLOW "Session models").

## 1. Classify

Run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" maturity` (all repos, a few git calls) and keep, per repo, only `mature`. Launch the `classifier` agent (model from `roles.classifier`) with the request, the repos with their roles and `mature: yes|no`, and the path of each source's index. Show its answer in one line: "Lane: feature (touches api and web). Say 'short' to change it."

If the user overrides, follow the user. If the classifier says `lane: task`, or the request is clearly a one-off check or cleanup across repos with nothing to design, or a long job (watching or operating something for hours or days), say in one line that `/home-office:task "<request>"` fits better and let the user choose (default: task). A long job runs there one step per session, with a hand-over note (`task` § "Long jobs").

**Minor fixes stay small.** Findings from an audit or a review, cleanups and style fixes go to the short lane or to `task`, never to the feature lane, unless one of them changes a contract or a schema (the classifier applies this; do not override it on your own). A long list of them runs as several short-lane changes or tasks, one per repo or per group of related fixes; anything left for later goes to the project's Backlog. Only the user can send minor fixes to the feature lane, and then the feature limit (`limits.tasks_per_feature`) still applies.

## 1b. Project

Every piece of work belongs to a **project** (one per repo; see "Projects" in `${CLAUDE_PLUGIN_ROOT}/core/WORKFLOW.md`). Take it from `--project <repo>` in the request (strip the flag; it must be a key of `repos`, else ask), or from the stream's `Project:` line if the work comes from a stream. Otherwise it is the repo the classifier lists first (the one that drives the work); if two repos are equally likely, ask in one line. Say it with the lane: "Project: api." Other repos the work touches are only "touched": they get a "touches" row on the board. If `<work>/projects/<repo>/project.md` is missing, create it from the `project.md` template (what it is: from the repo's knowledge card if there is one).

## 2a. Short lane

0. If the desktop tool `mcp__ccd_session_mgmt__set_session_title` exists, rename this session to `short: <name from the classifier>` (`session_id: "self"`).
1. Pick the repo (`<repo>` = its absolute path). Open an open-scope task on it, so hard rules and checks still apply:
   `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" task-start --worktree <repo> --task "short: <name>" [--delete <path>]… --deny "<glob>=<reason>"… --prepare "<cmd>"… --check "<cmd>"… [--advisory "<cmd>"]… --attempts <limits.task_attempts> --gate-seconds <limits.gate_seconds>`
   (`--deny` from the `guards` that apply to this repo; `--prepare` from its `prepare`; `--check` from its `checks`; `--advisory` from its `advisories`; no `--file`. `--delete` only for files or folders the request clearly says to remove, by exact path, after confirming the list with the user.)
2. Launch `home-office:implementer` (model from the role that matches the repo, else `roles.backend`). Its prompt starts with the line `HOME-OFFICE-WORKTREE: <repo>`, then: the request, the relevant knowledge sections (from the index), `hard_rules`, the paths it may delete (if any), the prepare commands and checks, the check command line (§ Execute step 3), and the limit of ~5 files (~10 in a mature repo: there, tell it to read the code and tests around the change first, as its guide, instead of expecting a plan).
3. Run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" task-end --worktree <repo> --report <the implementer's status>` and read `gate` (always `pass` or `fail`: it runs the checks itself if no gate ran) and `touched`. `fail`, `blocked` or `needs-plan-change` → tell the user (it may have outgrown the short lane; offer to restart it as a feature).
4. Launch `home-office:reviewer` on the uncommitted diff of that repo (one round, as in "Review → gate 3" below). Show `git -C <repo> diff --stat` and the review → **gate 3**: wait for the user. Fix only high and medium findings the user approves; low ones go as one line to the project's Backlog, not into this change, unless the user asks.
5. Propose a commit message → **gate 4**: the user commits. Give the commands as `git -C <repo> …` (see `close`): the session runs in the work folder.
6. Append one line to `<work>/<log>`: date, project, repo, what was done; also add it to the project's "Tasks done" in its `project.md`. Done.

## 2b. Feature lane

### Set up
1. Assign `NN`: the next free number in `<work>/features/` (two digits). Name: `NN-<name from the classifier>`.
2. Create `<work>/features/NN-name/` with `STATE.md` and `DECISIONS.md` from the templates. If the work belongs to a batch the user mentions, link it in `STATE.md` and the batch's repo table.
3. **Stream and project.** Write `Project: <repo>` in `STATE.md` (§ 1b). The feature belongs to a stream if the request has `--stream <name>` (strip the flag from the request), names a stream, or comes from `/home-office:stream next`. Resolve `<name>` (`NN`, `NN-name` or a unique part of the name) against `<work>/streams/`; if nothing matches, ask. Then: write `Stream: streams/NN-name` in `STATE.md` (otherwise `Stream: none`); in the stream's `stream.md` set this feature's roadmap row to `in progress` and fill its Link with `features/NN-name` (if the request matches no planned row, add one at the end); (a stream's `Project:` is the feature's project unless the user says otherwise). Pass `stream.md` to the explorer and the architect as shared decisions, like a batch's `DECISIONS.md`. Without a stream, write `Stream: none` and skip the roadmap part. Then move this session into the project's sidebar group (see `project` § "Sidebar group").
4. Add a row to the board: in the feature's project section (`## <repo>`, created if missing), under its stream heading (`### streams/NN-name`, created if missing) or under `### Other` if it has no stream. For each other repo the feature touches, add a row marked "touches" (with the driving project in the Work column) in that repo's section.
5. **Session title.** A hook titled this session "new: <request>". Rename it to `feat: NN-name #1` (this is the feature's first session) if the Claude desktop app's tool `mcp__ccd_session_mgmt__set_session_title` exists (it may be deferred: load it with ToolSearch `select:mcp__ccd_session_mgmt__set_session_title`), with `session_id: "self"`. Elsewhere, leave it. `resume` sessions get `feat: NN-name #n` from the hook, numbered in order (#2, #3…), so when you mention other sessions of the feature to the user, name them by that number.

### Explore
Launch `explorer` (`roles.explorer`) with the request, the brief template path and the destination `features/NN-name/brief.md`. Show its three-line summary and the link to the brief (see "Links to documents").

### SPEC → gate 1
Launch `architect` (`roles.architect`) in mode `spec`, with the brief, the template, `limits.tasks_per_feature` (default 8) and `limits.tasks_per_session`, and, if any, the batch's `DECISIONS.md` and the stream's `stream.md` (its shared decisions and roadmap; raise only what is new). Show the user the SPEC's goal, **what it unblocks**, its **size** (`Estimate:` — e.g. "~6 TASKs in 3 sessions, limit 8"; say so when it is over the limit), scope and **decisions needed** (with the architect's recommendations). **Wait for explicit approval.** Record the user's choices in the feature's `DECISIONS.md` and mark the SPEC approved with the date. If the user changes something, relaunch the architect in mode `spec` with the changes.

### PLAN + TASKS → gate 2
Launch `architect` in mode `plan` with the approved SPEC, the brief, the board, the templates and `limits.tasks_per_feature` (default 8). Show: the approach, the layers and repos, the contract in short, crossings, and the list of TASKs (title, repo, role, number of files, files to delete).

**Over the limit.** If the architect's first line says more TASKs than `limits.tasks_per_feature`, say it **before** asking for gate 2, with the numbers and its proposal, e.g. "14 TASKs, limit 8. The architect proposes splitting: TASKs 1–7 now (delivers …), the rest as a new feature." Let the user choose: **trim** or **split** (relaunch the architect in mode `plan` with that choice; what is left out goes as one line each to the Backlog of `<work>/projects/<repo>/project.md`, never to a hidden TASK), or **keep it** (only on the user's explicit word; record it in `DECISIONS.md`). Never ask for gate 2 on an over-limit PLAN without saying so.

**Wait for explicit approval.**

### Planned cut after gate 2
This session ends here; execution always starts in a fresh one. The conversation now holds the brief, SPEC and PLAN, and execution needs that room.
1. Rewrite `STATE.md`: status "executing — TASK 0 of y", "Next" = TASK 1 (title, repo, role), and the gate 1 and 2 dates under "Decisions this session".
2. Update the feature's row on the board.
3. Hand over (see "Handing over" below) with the line: "PLAN approved. Continue in a new session with `/home-office:resume NN-name`." Do not start any TASK in this session.

### Handing over
Every planned cut ends the same way, after `STATE.md` and the board's row are written. **Never skip step 1 when the tool exists**: a cut that only prints the command makes the user copy it and open a session by hand.
1. **Next session.** If the Claude desktop app's session tool `mcp__ccd_session__start_session` exists (it may be deferred: load it with ToolSearch `select:mcp__ccd_session__start_session`), call it before writing your final message. How depends on `handover` in `.home-office.yml` (default `card`):
   - `auto`, and the next step is **independent of every open wait**: it is not itself a gate, a push, a merge or another action that needs the user, and no TASK it depends on is behind a waiting row (`ho.py waiting list --feature NN-name`; STATE's "Blocked" names the ids). Open rows that block only other TASKs do **not** stop it: a feature can have waits and still hand over to the next independent TASK. **Start** it with `initiation: "user_asked"` — the user asked for automatic hand-overs in the project's config. Then say in one line that it has started, with a link to it.
   - Otherwise (`card`, or the next step itself waits for the user and nothing independent is left): **propose** it as a card with `initiation: "own_initiative"`; nothing runs until the user starts it with one click.
   When you **started** it (`auto`), detach it right away (`mcp__ccd_session_mgmt__detach_session` with its id) so it is not nested under this session. Move the new session into the feature's project sidebar group once it exists (`mcp__ccd_sidebar__move_sessions`, see `project` § "Sidebar group"); a card has no session until the user starts it, so `resume` does it then. Same fields either way: `context: "fresh"`, `use_worktree: false` (the session must open in this work folder, where the config is; the plugin makes its own worktrees), `model`: the full model id for `roles.conductor.model` (`roles.conductor` in `ho.py models`, § 0 step 7) when its tool is `claude` — without it the new session inherits this session's model, not the folder's default or the newest one, `title`: `feat: NN-name` (the hook adds its number, `#n`, when the session starts), `prompt`: `/home-office:resume NN-name`, and `background`: two sentences in `language` with the feature, its status and next step from `STATE.md`, and that everything lives in `features/NN-name/`. If the app refuses the start (for example on a turn another session started), fall back to the card.
2. **Text.** Always end with the cut's line too (`/home-office:resume NN-name`), so the hand-over works without the app (CLI, other clients) or if the card is refused.
3. Add that this session can be archived once the new one is running (a card lives in this conversation).
4. **One offer only.** The card (or the started session) is the only place the next session is offered. Do not ask about it again: no "Start the next session?" question, no button for it in the app's next-step box (a recap is enough), and no extra line asking to start it. If the user then says to start it ("start it", "yes", "go"), call `start_session` with **only** the card's `proposal_id`, never a new proposal.

### Execute
Runs in sessions opened with `/home-office:resume NN-name`. Each session executes at most `limits.tasks_per_session` TASKs (default 2), then cuts (step 8).

Agents are plugin agents: launch them as `home-office:<role>` (`home-office:backend`, `home-office:frontend`, `home-office:implementer`…), never by the bare name, which may be a different agent defined in the repo.

**Waits: never stop for one while independent work is left** (see "Waits" in `${CLAUDE_PLUGIN_ROOT}/core/WORKFLOW.md`). Whenever a TASK or step needs the user (a decision, a push, a merge, a check on staging, an environment or data, or a TASK marked `Waits:` in `TASKS.md`), do these three things, in order:
1. **File it.** `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" waiting add --kind <decision|push|merge|deploy-check|env|data|other> --project <repo> --work "NN-name / TASK n" --action "<the exact question or action; git commands as git -C <absolute repo path> …>" --blocks "<which TASK or step is stuck, or nothing else>"` (run it in the work folder; the helper stamps the time and the id `W-NNN`). Write `--action` and `--blocks` in `language`. Add the id to `STATE.md` "Blocked" (`W-NNN: <short>`).
2. **Say it in one line**: "W-007 waiting for you: push hub feature/07-x (blocks TASK 5)." Do not ask a question and stop.
3. **Continue with the next TASK that does not depend on it** (check `Depends on`, the files and the layer order) and open it as usual. Cut or hand over only when no independent TASK is left (the `tasks_per_session` budget still applies); then the cut says what waits.
The user's answers arrive in chat (or in a `status` or `resume` session): record each with `ho.py waiting answer W-NNN "<answer>"`, act on it, then `ho.py waiting acted W-NNN`, and clear its id from "Blocked". When acting changes where the feature stands (a merge, a publish, a deploy), update its `STATE.md` status line and "Next" and its board row in that same step, in whatever session acts on it. A push, a merge or a deploy is **never done by you**: you only file the row with the exact command. At the start of each TASK, `ho.py waiting list --state unacted --feature NN-name` shows answers nobody has acted on yet: act on them first.

For each TASK in order (respect `layers` and `Depends on`), reading from `TASKS.md` only that TASK:
1. **Worktree.** `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" worktree --repo <repo> --dest <worktrees>/<repo-name>/NN-name --branch feature/NN-name --base <repo base> [--copy <file>]… [--link <folder>]… [--setup "<cmd>"]…`
   (`<repo base>` is the repo's `base` if set, else `base_branch`. `--copy` (files or folders), `--link` and `--setup` come from the repo's `copy`, `link` and `setup` in the config; they only run when the worktree is created. A `link` folder (`vendor`, `node_modules`) is cloned from the main checkout with hard links in seconds when its lock file is identical, and its install command in `setup` is then skipped; `linked` in the result says which.) Reuse it for later TASKs in the same repo. If `ok` is false, stop and show the user the error.
2. **Open the TASK.** `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" task-start --worktree <wt> --task "NN-name / TASK n" --file <path>… [--delete <path>]… --deny "<glob>=<reason>"… [--prepare "<cmd>"]… --check "<cmd>"… [--advisory "<cmd>"]… [--setup "<cmd>"]… [--hotspot "<glob>"]… --base <repo base> --attempts <limits.task_attempts> --gate-seconds <limits.gate_seconds>`
   Files: the TASK's closed list — **a folder goes in as a glob, `<folder>/**`, never a bare `<folder>/`**: the scope guard matches each edited path against the list by exact path or glob, so a bare folder path matches no file and every edit under it is blocked (`--allow "<glob>"` is the same list, for patterns). Delete: the TASK's `Delete:` list, if any — the opposite convention, exact paths only, where a listed folder does cover everything under it. Deny: the `guards` that apply to this repo. Setup: the repo's `setup` (only used if the TASK changes a cloned folder's manifest or lock: then `task-start` replaces the clone with a real install). Prepare: the repo's `prepare` (run before the checks on every TASK: code generators and formatters). Checks: the repo's `checks`. Advisories: the repo's `advisories` (audits and the like: they run after the checks, never block). Gate seconds: `limits.gate_seconds` (default 540). Hotspots: the repo's `hotspots`; base: the repo's base branch (so unmerged feature branches count as claims). From now on the hooks block edits outside the list, Bash writes (except deleting the listed files), and finishing with failing checks.
   **Claims and hotspots** (see "Parallel features" in `${CLAUDE_PLUGIN_ROOT}/core/WORKFLOW.md`). `task-start` records the TASK's files as this feature's claims in the repo (shared by all its worktrees) and answers:
   - `conflicts: [{file, feature, task, since, source, hotspot?}]` → the TASK is open; say it in **one line** ("TASK 3 overlaps 04-x TASK 2 on `AdopterApiTest.php`") and follow the PLAN's "Crossings" (who goes first). If the PLAN does not say, or the other feature should go first, ask the user in that line.
   - `ok: false` with `hotspots_held` → another feature holds a hotspot this TASK lists; **nothing was opened**. Do not use `--force` on your own. Order the work: take the next independent TASK (`Depends on`, files, layers), and file a wait for this one (`ho.py waiting add --kind other --work "NN-name / TASK n" --action "wait for <feature> to merge or finish its TASK on <file>" --blocks "TASK n"`), looking at the inbox (`ho.py waiting list --feature NN-name`) for what else is pending; cut or ask only when nothing independent is left. Retry the TASK at the next session (`resume`): `task-end` and the merge release the claim. `--force` only on the user's word.
3. **Launch the executor** for the TASK's role (`home-office:backend`, `home-office:frontend`, or `home-office:implementer` for project-defined roles, passing the role's `description`), with the model from `roles.<role>`. The prompt's **first line** is `HOME-OFFICE-WORKTREE: <wt>`; then the TASK text, the path of `PLAN.md` (the executor reads its Contract section), the knowledge sections listed, `hard_rules`, the prepare commands and the checks, **and the check command line**: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" check --worktree <wt> --cmd "<check>"` (the path already resolved), with the instruction to run each full check only through it, once, when done, and to use only filtered tests while iterating. The result of a passing check is cached for the exact state of the files, so the gate and `task-end` that follow do not run it again. Pass nothing else.
   If the role's `tool` is not `claude`, delegate instead: run that tool's non-interactive mode with the worktree as its working directory and the same prompt. No checks gate runs for it: `task-end` in step 4 runs the checks itself.
4. **Close the TASK.** `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" task-end --worktree <wt> --report <status>` (`<status>`: the executor's `status:` line, e.g. `done`, `blocked`, `needs-plan-change`) → `gate` (always `pass` or `fail`), `touched`, `problems`, `advisories`, `rework`. When no checks gate ran (delegated work, a hook that did not fire), `task-end` runs the prepare commands, the scope check and the checks itself, so it can take as long as the checks: give the call your longest timeout. Called again, it repeats the last TASK's result. Update `STATE.md` (done / next) with the essentials only.
   **Trust the gate; never run the checks by hand.** `gate: pass` means the prepare commands, the scope check and every check already ran and passed: do not run them again. `gate: fail` carries the failing output in `problems`: read it there. Never launch `composer test`, `npm run …` or the like yourself to check a TASK: on big repos each run costs minutes. When you do need a full check (the pre-merge run in "Review → gate 3"), use `ho.py check`, never the bare command. Fixes go back to the executor. (`--no-checks` only closes a TASK dropped before any work, as `gate: skipped`.)
   **A gate cut by its time cap.** The app cancels hooks at about 600 s, so the checks gate stops itself at `gate_seconds` (default 540), kills the slow check and records `gate: timeout` (`task-status` shows it). That is not a failure: `task-end` runs what is left, with no cap, and does not repeat the checks that passed. It can take as long as the slowest check: run it in the background if your tool's timeout is shorter.
   **Advisories** (`advisories` in the result: command, `ok`, output tail) never change `gate`. Keep them for review: append them to `REVIEW.md` under "Advisories" (create the file from the template if it does not exist yet) and, when one found something (`ok: false`), add one line to the project's Backlog (`- Advisory <command> in <repo> (NN-name): <short finding> — features/NN-name/REVIEW.md`). Never turn them into TASKs unasked.
   **Rework is counted by `task-end`.** A TASK that goes back (`gate: fail`, or a `blocked` / `needs-plan-change` report) adds 1 to the `Rework:` line of the feature's `STATE.md`, once per TASK; `rework` in the result says so (`recorded`, `count`). `task-start` finds that `STATE.md` from `--task "NN-name / …"` and the config in the current folder (`state` in its result; pass `--state <path>` if it is null). Never change that line by hand; if you edit `STATE.md` after `task-end`, reread its header first.
5. **Commit.** A TASK with `gate: pass` and report `done` gets its own commit on `feature/NN-name` in its worktree, message `NN-name / TASK n: <title>`. The scope file is gone after `task-end`, so the hooks allow it. Stage only that TASK's files: the `touched` list `task-end` printed (deletions included), or, if it is empty because no gate ran, the TASK's file list plus its `Delete:` paths: `git -C <wt> add -A -- <touched>…`, then `git -C <wt> commit -m "<message>"`.
   - `commit: auto`: commit now and note the SHA in `STATE.md` ("Done").
   - `commit: ask` (default): note the TASK as "passed, not committed" and ask once per session, at the planned cut (step 8) or when execution ends: "Commit TASKs x, y on feature/NN-name?", with the proposed messages. Commit only on the user's yes, one commit per TASK, in order (keep each TASK's `touched` list in `STATE.md` until then).
   - Never commit on the base branch, never push, amend or rebase, and never skip hooks. Files written by `prepare` that git ignores stay out by themselves; tracked ones go in.
6. **Decide.** `gate: pass` and report `done` → next TASK. Anything else (`gate: fail` — the executor already had `task_attempts` tries inside its run —, `blocked`, `needs-plan-change`, or delegated work out of scope) → **no new attempt**: file it as a wait (kind `decision`, or `env` / `data`; `--blocks` the TASK and whatever depends on it), write its id under "Blocked" in `STATE.md` (`task-end --report` already counted the rework), say it in one line and go on with the next independent TASK, as in "Waits" above. Ask the user in the message only when nothing independent is left.
7. If a TASK needs interactive tuning (browser, emulator, simulator, editor), finish the others first (the tuning is a wait of kind `other`: file it), then tell the user to open a session in that worktree and run `/home-office:resume NN-name --tuning`.
8. **Planned cut.** After `limits.tasks_per_session` TASKs in this session, stop even if the context looks fine. First settle step 5's commits (with `ask`, the one question; the SHAs go to `STATE.md` "Done"). Then make sure `STATE.md` says "TASK x of y", names the next TASK (or "review" if they are all done) and lists the open waiting ids under "Blocked", update the board's row, and hand over (see "Handing over") with the line: "Continue in a new session with `/home-office:resume NN-name`."

### Review → gate 3
A **round** is one pass of `reviewer`, plus `deep-reviewer` when it applies. Count the rounds already done from the sections of `features/NN-name/REVIEW.md` (one per round), if it exists.

0. **Checks before the merge.** Before launching the reviewers, run the full checks once more, through the cache, for every repo the feature touched: for each, `ho.py check --worktree <wt> --cmd "<check>"` (all of the repo's `checks`, in its feature worktree). Where nothing changed since the TASK's gate they come back `cached: true` in a fraction of a second. If a **shared package** (`shared_packages`) changed, also run the checks of the repos that consume it (the PLAN's "Shared packages" section or the knowledge cards say which), in their feature worktree if they have one, else in their checkout; one run each, through the cache. A failure is a high finding at gate 3 (`REVIEW.md`), not a reason to rerun it by hand.
1. **Round 1.** Launch `reviewer` (`roles.reviewer`) on the feature branches against each repo's base (`base`, else `base_branch`) in every repo touched. If any changed path matches `risk_zones`, also launch `deep-reviewer` (`roles.deep-reviewer`). Tell both the round number and that only high and medium findings (critical too, for the deep reviewer) lead to fixes.
2. **REVIEW.md.** Write their findings to `features/NN-name/REVIEW.md` from the template (one dated section per round, newest first, in `language`; the reviewers are read-only, so you write it from their reports). Low findings are written there and nowhere else in the feature.
3. **Low findings go to the backlog.** If the round has low findings, add one line to the Backlog of `<work>/projects/<repo>/project.md` (create the page from the template if missing): `- Low review findings of NN-name (<n>) — features/NN-name/REVIEW.md`. They **never** become TASKs, fixes or another round, unless the user asks for it in so many words.
4. **Gate 3.** Show `git diff --stat` per repo, the findings by severity (low ones as a count: "4 low, recorded in REVIEW.md and the backlog") and the link to `REVIEW.md`. **Wait for the user.**
5. **Fixes.** Only high and medium findings, and only those the user approves, go back through executors as new TASKs appended to `TASKS.md` (as few as possible); say the new total against `limits.tasks_per_feature` if it goes over.
6. **More rounds.** The feature gets `limits.review_rounds` rounds (default 1). After that, one more round runs **only** if the last one had high or medium findings, once their fixes are done, and it reviews **only the fixes** (the commits since that round), not the whole diff again. A round with no high or medium findings ends the review: go to close.

### Close → gate 4
When the user has accepted gate 3 and nothing is left to fix (no high or medium finding pending, no low one the user asked to fix; the other lows are in `REVIEW.md` and the backlog), every TASK in `TASKS.md` is done and committed (with `commit: ask`, ask now; on a no, stop here and say the feature closes once committed), run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" close-ready --feature NN-name --worktree <wt>…` (every worktree of the feature). With `ready: true`, by `close` in the config: `card` (the default) proposes it for one click: in the Claude desktop app, end the turn with the next-step box (`mcp__ccd_turn__wrap_up`) asking, in `language`, whether to close NN-name, with one reply button meaning "Yes, close it" (elsewhere, that one-line question); on the user's yes run the `close` procedure yourself (the `home-office:close` skill), and on anything else do not ask again this session. `auto` runs it at once, with no question. `ask` tells the user to run `/home-office:close`. With `ready: false`, say in one line what is missing (its `blockers`) and propose nothing. The pushes and merges close proposes are filed in the waiting inbox, not left in prose.

## Links to documents

Whenever a step writes or updates a document, end that message with one line of links so the user can open each one with a click, e.g. `Read: [brief](docs/work/features/07-x/brief.md) · [SPEC](docs/work/features/07-x/SPEC.md)`.
- Markdown links, with paths relative to the current working directory (the folder with `.home-office.yml`) and forward slashes. Most clients make them clickable; the Claude desktop app opens them in its file pane.
- Label them with the document's name in `language`.
- Link only what this step wrote or changed: brief after Explore; SPEC at gate 1; PLAN and TASKS at gate 2; `STATE.md` after each TASK and at every cut; `REVIEW.md` at gate 3; `STATE.md` and `DECISIONS.md` at close.
- Files inside worktrees are outside this folder and may not open from here: name them as `path` in code, never as links.
- Links never replace the summary the step asks for: the user decides from the summary and reads the documents when they want.

## Context discipline

- Pass each subagent only what its role needs. Never paste whole files into prompts; pass paths.
- From each subagent's report keep only its status line (`status: …`, the gate result and one line of notes); the rest is in the files. Never reread the SPEC or the PLAN in full: subagents read them by path, and you read only the TASK you are about to open.
- Sessions are cut on purpose, not when they are full: after gate 2, and after `limits.tasks_per_session` TASKs. Each cut writes `STATE.md` and hands over to `/home-office:resume NN-name` (card plus text line, see "Handing over").
- If this conversation still becomes long (near `limits.context_tokens`), cut the same way at once.
