# /home-office:resume

You continue a feature as its **conductor** (or, with `--tuning`, as the interactive tuning session). The past conversation does not matter: the files do.

1. **Where.** In tuning mode the session is opened in a repo worktree: find the work folder from the argument path or ask the user for it. In any other mode, `.home-office.yml` must be in the current working directory; if it is not, stop and tell the user where to open the session. Pick the feature: the argument ($ARGUMENTS) (`NN` or `NN-name`); without it, read the board and ask which one (list the ones in flight).
2. **One call for everything.** Run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" resume-brief --feature <NN or NN-name> --sync` (no `--sync` in `--tuning`, or with `commit: ask` and TASKs "passed, not committed" in `STATE.md`). It prints, as one JSON object:
   - `state`: the whole `STATE.md` (it may be in another language: find each section by its position in the template), `status_word`, `documents` (which of brief, SPEC, PLAN, TASKS, REVIEW exist);
   - `next_task`: the text of the TASK that "Next" names, from `TASKS.md` (`null` when "Next" names none, e.g. the review), and `tasks_total`;
   - `waiting`: the feature's open rows and answered rows not yet acted on;
   - `worktrees`: each repo's feature worktree and base, with `sync`, the result of merging the base into it;
   - `next_session_title`: the title for this feature's next hand-over;
   - `config`: what a conductor uses from `.home-office.yml` (`settings`, `limits`, `roles` with full model ids, the raw entries of the feature's `repos`, `hard_rules`, `guards`, `risk_zones`).
   Do **not** open `.home-office.yml`, `TASKS.md` or `waiting.md`: read the config only for a key that is missing in `config`, and from `TASKS.md` only another TASK you are about to open. Never read the SPEC, PLAN or brief in full: subagents read them by path; if a step needs one detail, read only that section. Then read `${CLAUDE_PLUGIN_ROOT}/core/EXECUTE.md` once: it is the procedure from here on (hand-overs, execution, review, close). Do not open `skills/new/SKILL.md`.
3. **Act on the brief.**
   - **Waits.** Answered rows not yet acted on come first: before any TASK, take each (`ho.py waiting take W-NNN --by "<this session's title>"`; one with `taken_by` another session is that session's: leave it) and act on it (carry out what the answer says, e.g. continue the TASK it unblocked), then `ho.py waiting acted W-NNN` and clear its id from `STATE.md` "Blocked". Open rows stay as they are: they are what the next TASKs must work around (`core/EXECUTE.md` § Execute, "Waits"). If the user answers one in this session, `ho.py waiting answer W-NNN "<answer>"` at once.
   - **Sync.** `up_to_date` and `merged` need nothing (mention `merged` with its files in one line). `refused` is fine (say why only if `dirty`). **`conflict`** (the helper already aborted: everything is as it was, `files` lists them) is **never fixed by hand by you**: if the conflict is in a file of a TASK still to do, add its resolution to that TASK's instructions or propose a small new TASK "merge `<base>` into the feature" (files = `files`; it needs a TASK because the merge touches them), and tell the user in one line; otherwise file a wait (`ho.py waiting add --kind other …`) with the files and carry on with independent TASKs. A worktree created later in this session is synced by `ho.py sync --worktree <wt> --base <repo base>`.
4. Tell the user in three lines where it stands: status, next step, anything blocked (the open waiting ids, with their age); then one line of links to `STATE.md` and the feature's documents that exist, as in `new` § "Links to documents".
5. Continue from "Next" following `core/EXECUTE.md` from that point (execution, review or close). Gates still apply. **A wait is not a stop**: when a TASK or step needs the user, file it (`core/EXECUTE.md` § Execute, "Waits": `ho.py waiting add`, one line to the user) and continue with the next TASK that does not depend on it; ask for the answer in the message only when nothing independent is left. If "Next" itself is a TASK behind an open wait, take the next independent one from `TASKS.md` instead.
   **Review (gate 3)** follows `core/EXECUTE.md` § "Review → gate 3" in full: count the rounds already done from the sections of `REVIEW.md`; `limits.review_rounds` rounds (default 1), and one more only when the last round had high or medium findings and their fixes are done, reviewing only those fixes. Low findings go to `REVIEW.md` and one line in the project's Backlog; never turn them into TASKs or another round unless the user asks. Fix TASKs that take the feature over `limits.tasks_per_feature` (default 8) are said with the number before they start.
6. **App housekeeping** (Claude desktop app only; in `--tuning`, title and sidebar only, at the start): do it **after** launching the first executor, while it runs, never before the first TASK. Load the tools you need in one ToolSearch call (`select:mcp__ccd_session_mgmt__get_session,mcp__ccd_session_mgmt__list_sessions,mcp__ccd_session_mgmt__archive_session,mcp__ccd_session_mgmt__detach_session,mcp__ccd_sidebar__list_groups,mcp__ccd_sidebar__move_sessions`), then one `mcp__ccd_session_mgmt__get_session` with "self":
   - **Title.** The title hook and the hand-over already name this session `feat: NN-name #n`. Rename it (`mcp__ccd_session_mgmt__set_session_title`, "self") only when the title `get_session` shows has no `#n`: `feat: NN-name #<highest number in sessions.json>`, plus ` · tuning` in tuning mode.
   - **Previous session.** If it shows a `parentSessionId`, get the parent: when its title is `feat: NN-name` of this same feature (or it handed over from this feature) and it is idle, archive it with `mcp__ccd_session_mgmt__archive_session` and a reason like "replaced by the next session of NN-name". With `archive: ask` ask the user once first, in one line; with `auto` just do it (the app may still ask for approval). Archiving a session also archives its finished, idle side sessions, so first list the parent's children (`list_sessions`): archive only if this session is its only child still alive; if another idle child is still in use, skip it, or detach this session first if that makes it safe. If the call is refused, follow `project` § "Archiving sessions".
   - **Sidebar group.** If this session has a `parentSessionId` and is not `detached`, detach it (`mcp__ccd_session_mgmt__detach_session`, "self") so it sits at the top level, then move it into the group of the project in `STATE.md`'s `Project:` line (`project` § "Sidebar group"); without that line, use the first repo of `Branches`, else skip.
   Without these tools (CLI), skip this step.
7. **Planned cut.** Keep executing TASKs, and go on to the review and the close, until the planned cut of `core/EXECUTE.md` § Execute step 8: the context hook's "Planned cut point reached" message (`limits.cut_at`) or `limits.tasks_per_session` TASKs in this session, whichever comes first. Keep only each report's status line. Then: first the commits of step 5, then `STATE.md` with "TASK x of y" and the next TASK, `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" board --write`, and the hand-over of `core/EXECUTE.md` § "Handing over": when the desktop app's session tool exists, **always** start the next session (`handover: auto` and the next TASK is independent of the open waits) or propose it as a card — never only the text line — with `title`: `next_session_title` from the brief, plus the line "Continue in a new session with `/home-office:resume NN-name`."

## Tuning mode (`--tuning`)

The only session that works directly with the user on a running app (browser, emulator, simulator, editor).
- Work inside the feature worktree only. Before the first change, open the tuning task so the guards apply: `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" task-start --worktree <wt> --task "NN-name / tuning" --state <work folder>/<work>/features/NN-name/STATE.md --file <files of the TASK being tuned>… [--delete <path>]… [--prepare "<cmd>"]… --check "<cmd>"…`. If a change needs another file, ask the user and restart the task with the extra file (`--force`).
- Count the user's tuning requests. At `limits.tuning_requests` (or near the context cap), write what is left to `STATE.md` under "Next" and tell the user to run `/home-office:close` and reopen.
- Before closing, run `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" task-end --worktree <wt>` (no checks gate runs in tuning, so it runs the prepare commands, the scope check and the checks itself, and counts a `fail` as rework in `STATE.md`); record the result in `STATE.md`. While tuning, run only filtered tests; a full check goes through `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/ho.py" check --worktree <wt> --cmd "<check>"`, whose cached pass makes that `task-end` instant.
